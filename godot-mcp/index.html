godot-mcp

An MCP server that lets coding agents see and play Godot games like a person would.

  • MCP
  • ADB

Coding agents can write a game but can’t see it. godot-mcp gives them eyes and hands: they take a screenshot, look at it, click or press keys, and take another one.

It works with any Godot 4 game. One call installs a small bridge into the project, and from then on the agent can launch it and play.

Why it exists

The first attempt took screenshots with the desktop compositor. That races the game window, and short runs would close before the window was ever captured. The engine can always save its own pixels mid-run, so the screenshots come from inside the game instead.

Two halves, one rule

An autoload inside the game listens on localhost and runs screenshots, input and scene-tree dumps. A Python MCP server starts and stops the game, forwards the tools and returns screenshots as images. The rule between them is that everything is in screenshot pixels: if the agent sees a button at a point in the image, clicking that point hits the button.

That took a couple of goes. The first version converted coordinates for the engine’s stretch mode before sending them, then the engine applied its own stretch on top, and every click missed. Now the bridge only corrects for the window and HiDPI and lets the engine do the rest.

The scene tree as a cheat sheet

The tree tool dumps the running scene with every control’s rectangle in screenshot pixels, plus the text on buttons and labels. The agent doesn’t have to guess where “Play Again” is from the picture, it can just read it.

Phones too

For Android it uses adb instead of the bridge. It installs the APK, launches it, takes screenshots, and taps, swipes and long-presses at the same coordinates as the screenshot, then reads logcat. That’s how the phone games here get tested on a real device.

Careful with input

  • Input is sent exactly once. If a reply goes missing, the tool returns an error rather than risk a double click.
  • Setup backs up the project file and checks the patch, and launch refuses to run until setup is done.
  • The bridge only listens on localhost and is for development only, never for a shipped build.

Limits

  • It needs a display. A headless run has no picture to send.
  • It covers mouse, keyboard and input actions, so menus, shops and board games. Analogue sticks still need something else.
