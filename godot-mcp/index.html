godot-mcp

An MCP server that lets coding agents see and play Godot games like a person would.

Coding agents can write a game but they can’t see it. I found that out the annoying way, back in September my Godot skill would launch the game with an 8 second timeout, then check for the window after the timeout had already killed it. godot-mcp is the fix for that. It gives agents eyes and hands, they take a screenshot, look at it, click or press keys, and take another one.

It works with any Godot 4 game. One call installs a small bridge into the project, and from then on the agent can launch it and play. Every Godot game I work on gets the bridge now, and it’s how my agents test the games on this site, as much as possible.

How it works

The first attempt took screenshots with the desktop compositor, which races the game window, so short runs would close before the window was ever captured. The engine can always save its own pixels mid-run, so the screenshots come from inside the game instead.

So there are two halves. An autoload inside the game listens on localhost and handles screenshots, input and scene-tree dumps, and a Python MCP server starts and stops the game, forwards the tools and returns screenshots as images. The rule between them is that everything is in screenshot pixels, if the agent sees a button at a point in the image, clicking that point hits the button.

That took a couple of goes. The first version converted coordinates for the engine’s stretch mode before sending them, then the engine applied its own stretch on top, and every click missed. Now the bridge only corrects for the window and HiDPI and lets the engine do the rest.

The tree tool is a bit of a cheat sheet. It dumps the running scene with every control’s rectangle in screenshot pixels, plus the text on buttons and labels, so the agent doesn’t have to guess where “Play Again” is from the picture, it can just read it.

Phones

A lot of my games are for Android, so in October I added phone support. It uses adb instead of the bridge, installs the APK, launches it, takes screenshots, taps, swipes and long-presses at the same coordinates as the screenshot, then reads logcat. That’s how the phone games here get tested on a real device.

Being careful with input

  • Input is sent exactly once. If a reply goes missing, the tool returns an error rather than risk a double click.
  • Setup backs up the project file and checks the patch, and launch refuses to run until setup is done.
  • The bridge only listens on localhost and is for development only, never for a shipped build.

What it can’t do

  • It needs a display. A headless run has no picture to send.
  • It covers mouse, keyboard and input actions, so menus, shops and board games are fine. Analogue sticks still need something else.
