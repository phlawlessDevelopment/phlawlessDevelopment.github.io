Case study · Last updated 2 November 2026

A real-time chat app with a built-in AI facilitator. It watches each room for a conversation that is turning hostile and, when one needs help, posts a single neutral, practical intervention, then steps back for a cooldown.

Before you try the demo

  • Sign-up is open. Use a throwaway username and a password you do not use anywhere else (12 characters or more).
  • Do not post anything private. Messages are stored unencrypted in the demo database, and there is no password recovery or account deletion yet. Nothing is guaranteed to be kept.
  • While a room is calm, each message, the sender’s username and a few earlier messages are sent to TypeSafe to be scored. If a room is flagged, the triggering message and up to 12 earlier ones are sent to OpenAI to write the reply.
  • AI calls run on a fixed allowance. When it is used up, chat keeps working but the mediator stays quiet.
  • To see it act, create a room and post something heated. It works with just one account, but it is threshold-based, so mild messages will not trigger it.

What it does

People register, create rooms, and invite others by username. Rooms are invite-only: an invitee sees nothing until they accept. Messages are saved, so history survives a refresh, and they arrive live over a WebSocket. The interface has a searchable conversation list, light and dark themes, per-room drafts and keyboard shortcuts.

The twist is an automated participant. When a conversation escalates, a message labelled Mediator · AI facilitator appears in the room. It is grounded in what was actually said, offers one practical next step and asks at most one question. It is stored and delivered like any other message, but it is always visibly marked as automated.

How a message becomes an intervention

  1. Save, then announce. The message is committed and an event is published. Classification runs asynchronously after commit, so sending a message never waits on an AI call.
  2. Score. A classifier sends the message and a few earlier ones to TypeSafe’s Jev, which rates seven independent signals (personal attack, contempt, passive aggression, dismissiveness, motive attribution, inflammatory wording, retaliation) and a four-level hostility score. The history window is bounded by the reviewed message’s own timestamp and ID, so a queued job can never see later messages.
  3. Decide in application code. Jev only scores. A policy class combines the signals with thresholds and weights into CLEAR, BORDERLINE, TRIGGER or UNAVAILABLE. Two borderline results within a room’s last six classified messages also trigger. A classifier failure counts as UNAVAILABLE and chat carries on.
  4. Claim the room. On a trigger, one conditional SQL UPDATE moves the room from CALM to MEDIATING. Only the caller that changes a row publishes the request, so simultaneous triggers produce exactly one intervention.
  5. Generate, outside any transaction. A bounded worker claims the persisted request with a token, loads the trigger’s context and calls the model. The database is not held during the call, so the rest of chat stays responsive. The conversation is passed as data, separate from the instructions, and the model has no tools and no view of other rooms.
  6. Publish, then cool down. Finishing the request stores the mediator message and starts the room’s cooldown in one atomic step, and the message is broadcast only after that commits. Automated messages are never classified, so the mediator cannot trigger itself.

Engineering decisions

Prefer a missed reply to a duplicate bill

If the process dies mid-request, work nobody had claimed is resubmitted, but a claimed request is allowed to expire instead of being generated again. Finishing a request must match the room, the trigger ID and the claim token, so a slow or obsolete worker cannot post into a newer session. Anything older than 60 seconds expires into cooldown, and a message sent before the previous cooldown ended cannot immediately re-trigger the room.

A spend ceiling that lives in the database

Every external call reserves from a persistent allowance (by default 100 classifications and 20 replies per provider) before any network I/O, and failed calls count. The counters survive restarts. Once the allowance is spent, chat is unaffected and the mediator stays quiet. It is a request cap, not a dollar cap, and the docs say so.

Authorisation where the data actually flows

Membership is checked on REST calls and on every STOMP subscribe and send. Delivery also rechecks the recipient’s current session and membership, so leaving a room or logging out cuts off a socket that is already open. The release audit found the first version kept delivering after a user left; it is now covered by an end-to-end test over a real HTTP and WebSocket connection.

Single-writer SQLite, on purpose

One connection, WAL mode, and a schema owned by Flyway migrations and checked at startup. Keeping model calls out of transactions is what lets one connection serve a live chat. The design is single-instance by choice; scaling out would mean PostgreSQL and an external message broker, and the docs say that too.

Swappable providers, safe failures

The classifier is a port with a no-op fallback, so the app runs with no API keys. The OpenAI and Anthropic adapters are thin HTTP clients with a timeout, an output cap, a response-size cap and no automatic retries. Any provider failure becomes a plain system notice and a cooldown. Raw provider errors are neither logged nor shown to users.

Security and operations

  • Application: server-side sessions, BCrypt passwords, CSRF protection on HTTP and on the STOMP connect frame, a content security policy and related headers, bounded request bodies, per-IP and per-user rate limits, and caps on connections and subscriptions.
  • Container: runs as a non-root user with a read-only filesystem and dropped capabilities. Only the Caddy proxy is reachable from the internet, and SSH is restricted to the administrator’s address.
  • Images: scanned with Trivy. The official Caddy image had nine fixable high or critical findings, so the proxy is rebuilt on a patched Go toolchain and libraries, and that image scans clean.
  • Backups: a nightly online SQLite backup, integrity-checked, encrypted to a public certificate and uploaded to private object storage. The host’s credentials can add backups but not read or delete them, so a compromised host cannot destroy its own history. The decryption key is kept off the server. A restore into an isolated copy has been rehearsed.

A bug that only appeared on real hardware

The test suite was green, but the container had never actually been run. On the Oracle host it crash-looped on startup. Docker mounts tmpfs with noexec by default, and the SQLite JDBC driver extracts a native library at startup that has to be mapped as executable. The fix was a small dedicated tmpfs that allows execution, owned by the app user and used only by the driver, leaving /tmp locked down. It was verified across a restart and a full container recreate.

Verification

  • 134 backend tests cover the API and CSRF, validation, membership, invitations, history bounds, the policy, atomic transitions, concurrent workers, timeout and restart recovery, late replies and provider contracts. One end-to-end test sends a message and follows it through the trigger and an asynchronous model stub to live delivery, while another user’s message arrives mid-generation.
  • 16 frontend tests run on Node’s built-in test runner with no dependencies. They cover reconnects, stale callbacks, message ordering and de-duplication, the AI label, and rendering model output as text rather than HTML.
  • Against the deployed system: a script of about twenty checks covers anonymous and CSRF rejection, cookie flags, an uninvited account’s access, live WebSocket delivery, persistence and revocation. A further run exercised a real classification and reply. The intervention reached other members in two to three seconds.
  • Dependencies: Maven runtime packages and the vendored STOMP bundle were checked against the OSV advisory database, and the container images were scanned.

Limits and what comes next

  • Reply quality is not formally evaluated. What has been verified is the connection and the lifecycle. The replies seen so far read as neutral and specific, but that is a judgement by eye, not a measurement. A labelled dataset of expected outcomes exists in the repository but is not yet wired into the tests; that is the next step.
  • Single instance. The in-process message broker and SQLite are a deliberate trade-off for a small deployment.
  • Not production-complete as a product. Conversations are stored in plaintext, and password recovery, email verification, account deletion and moderation tooling are not built.
