Write-up · Last updated 2 November 2026

It’s a chat app with an AI mediator sitting in every room. It reads along, and when a conversation starts turning nasty it posts one calm, practical message, then backs off for a while.

The chat side is pretty standard. The interesting bit is everything around the model call, making sure it only ever steps in once, never pays for the same reply twice, can’t blow through its budget, and stops sending you messages the moment you leave a room.

Before you try the demo

  • Sign-up is open. Use a throwaway username and a password you don’t use anywhere else (12 characters or more).
  • Don’t post anything private. Messages are stored unencrypted in the demo database, there’s no password reset or account deletion in the app yet, and I’m not promising to keep anything.
  • While a room is calm, each message, the sender’s username and a few earlier messages get sent to TypeSafe to be scored. If a room gets flagged, the message that set it off and up to 12 earlier ones go to OpenAI to write the reply.
  • AI calls run on a fixed allowance. Once that’s used up, chat still works but the mediator goes quiet.
  • To see it do its thing, make a room and post something heated. One account is enough, but it works off thresholds, so mild stuff won’t set it off.

What it does

You sign up, make rooms and invite people by username. Rooms are invite-only, so you don’t see anything until you accept. Messages are saved, so the history survives a refresh, and new ones come in live over a WebSocket. There’s a searchable conversation list, light and dark themes, a draft per room and keyboard shortcuts.

The twist is the extra participant. When a conversation escalates, a message labelled Mediator · AI facilitator shows up in the room. It sticks to what people actually said, suggests one practical next step and asks one question at most. It’s stored and delivered like any other message, but it’s always clearly marked as automated.

How a message turns into an intervention

  1. Save, then announce. The message gets committed and an event is published. Scoring runs asynchronously after the commit, so sending a message never waits on an AI call.
  2. Score. The classifier sends the message and a few earlier ones to TypeSafe’s Jev, which rates seven separate signals (personal attack, contempt, passive aggression, dismissiveness, motive attribution, inflammatory wording, retaliation) plus a four-level hostility score. The history window stops at the reviewed message’s own timestamp and ID, so a job sitting in the queue can’t peek at later messages.
  3. Decide in our own code. Jev only scores, it doesn’t decide anything. A policy class combines the signals with thresholds and weights into CLEAR, BORDERLINE, TRIGGER or UNAVAILABLE. Two borderline results within a room’s last six scored messages also count as a trigger. If the classifier fails it’s UNAVAILABLE and chat carries on.
  4. Claim the room. On a trigger, one conditional SQL UPDATE moves the room from CALM to MEDIATING. Only the caller that actually changed a row publishes the request, so if two triggers land at once you still get exactly one intervention.
  5. Generate, outside any transaction. A bounded worker claims the saved request with a token, loads the context and calls the model. Nothing holds the database during the call, so the rest of the chat stays responsive. The conversation goes in as data, separate from the instructions, and the model has no tools and can’t see other rooms.
  6. Publish, then cool down. Storing the mediator’s message and starting the room’s cooldown happen in one atomic step, and the message only gets broadcast after that commits. Automated messages are never scored, so the mediator can’t set itself off.

The decisions behind it

Better to miss a reply than pay for one twice

If the process dies mid-request, anything nobody had claimed yet gets resubmitted, but a claimed request is left to expire instead of being generated again. Finishing a request has to match the room, the trigger ID and the claim token, so a slow or stale worker can’t post into a newer session. Anything older than 60 seconds expires into cooldown, and a message sent before the last cooldown ended can’t instantly re-trigger the room.

A spending cap that lives in the database

Every external call reserves from a saved allowance (by default 100 classifications and 20 replies per provider) before it touches the network, and failed calls still count. The counters survive restarts. Once it’s spent, chat is fine and the mediator just goes quiet. It’s a cap on requests, not on money, and the docs say so.

Checking permissions where the data actually goes

Membership is checked on REST calls and on every STOMP subscribe and send. Delivery also rechecks the recipient’s current session and membership, so leaving a room or logging out cuts off a socket that’s already open. The release audit caught the first version still delivering messages after someone had left. There’s now an end-to-end test for that over a real HTTP and WebSocket connection.

SQLite with one writer, on purpose

One connection, WAL mode, and a schema owned by Flyway migrations and checked at startup. Keeping model calls out of transactions is what lets a single connection handle a live chat. It’s single-instance by choice. Scaling out would mean PostgreSQL and a proper message broker, and the docs say that too.

Swappable providers that fail quietly

The classifier sits behind an interface with a do-nothing fallback, so the app runs without any API keys at all. The OpenAI and Anthropic adapters are thin HTTP clients with a timeout, an output cap, a response-size cap and no automatic retries. Any provider failure turns into a plain system notice and a cooldown. Raw provider errors never get logged or shown to anyone.

Security and running it

  • The app: server-side sessions, BCrypt passwords, CSRF protection on HTTP and on the STOMP connect frame, a content security policy and the related headers, size limits on request bodies, rate limits per IP and per user, and caps on connections and subscriptions.
  • The container: runs as a non-root user with a read-only filesystem and dropped capabilities. Only the Caddy proxy is reachable from the internet, and SSH only accepts my IP.
  • Images: scanned with Trivy. The official Caddy image had nine fixable high or critical findings, so the proxy gets rebuilt on a patched Go toolchain and libraries, and that one scans clean.
  • Backups: a nightly online SQLite backup, integrity-checked, encrypted to a public certificate and uploaded to private object storage. The server’s credentials can add backups but can’t read or delete them, so a compromised server can’t wipe its own history. The decryption key isn’t on the server. A restore into a separate copy has been tested.

A bug that only showed up on the real server

All the tests were green, but the container had never actually been run. On the Oracle box it crash-looped on startup. Docker mounts tmpfs with noexec by default, and the SQLite JDBC driver unpacks a native library at startup that has to be executable. The fix was a small dedicated tmpfs that allows execution, owned by the app user and only used by the driver, so /tmp stays locked down. It’s been checked across a restart and a full container recreate.

How it’s tested

  • 134 backend tests cover the API and CSRF, validation, membership, invites, history bounds, the policy, atomic transitions, concurrent workers, timeouts and restart recovery, late replies and provider contracts. One end-to-end test sends a message and follows it through the trigger and a fake async model all the way to live delivery, while another user’s message lands mid-generation.
  • 16 frontend tests run on Node’s built-in test runner, no dependencies. They cover reconnects, stale callbacks, message ordering and de-duplication, the AI label, and making sure model output gets rendered as text, not HTML.
  • Against the live server: a script of about twenty checks covers anonymous and CSRF rejection, cookie flags, what an uninvited account can get at, live WebSocket delivery, persistence and revocation. Another run did a real classification and reply, and the intervention reached the other members in two to three seconds.
  • Dependencies: the Maven runtime packages and the vendored STOMP bundle were checked against the OSV advisory database, and the container images were scanned.

What it doesn’t do yet

  • Reply quality isn’t properly measured. What’s been verified is the plumbing and the lifecycle. The replies I’ve seen read as neutral and specific, but that’s me eyeballing them, not a measurement. There’s a labelled dataset of expected outcomes in the repo that isn’t wired into the tests yet, and that’s next.
  • It’s one instance. The in-process message broker and SQLite are a deliberate trade-off for something this small.
  • It’s not a finished product. Conversations are stored in plaintext, and there’s no password recovery, email verification, account deletion or moderation tooling yet.
