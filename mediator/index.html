Write-up · Last updated 16 November 2026

I’ve wanted to make this for a while. Back in 2024 I had a go at a “mediator” chatbot in Laravel, using Google’s moderation API to decide when it should speak up, and I generated a load of fake arguments between two made-up people (Alyce and Billy) to test it. This is the second attempt, and this time it’s actually running somewhere you can use it.

The idea is pretty simple. It’s a normal chat app, rooms, invites, history, messages coming in live, with one extra participant. The mediator reads along, and when someone gets out of line (a personal attack, contempt, passive aggression, putting motives in someone else’s mouth etc.) it posts one calm message, then backs off for a while. I wanted it to act like a real mediator or couples counsellor would, so it sticks to what people actually said, suggests one practical next step and asks one question at most. It’s always labelled as Mediator · AI facilitator, it’s not pretending to be a person.

Before you try the demo

  • It’s behind a password at the moment, so email me if you want a go.
  • Use a throwaway username and a password you don’t use anywhere else (12 characters or more).
  • Don’t post anything private. Messages are stored unencrypted, there’s no password reset or account deletion in the app yet, and I’m not promising to keep anything.
  • While a room is calm, each message, the sender’s username and a few earlier messages get sent to TypeSafe to be scored. If a room gets flagged, the message that set it off and up to 12 earlier ones go to OpenAI to write the reply.
  • The AI calls run on a fixed allowance. Once that’s used up, chat still works but the mediator goes quiet.
  • To see it do its thing, make a room and post something heated. One account is enough, but it works off thresholds, so mild stuff won’t set it off.

How it decides when to step in

Getting a model to write a calm reply is honestly the easy part. The hard part is everything around it, making sure it only steps in once, never pays for the same reply twice, can’t burn through my API budget, and stops sending you messages the moment you leave a room.

When you send a message it gets saved first, and the checking happens afterwards, so sending a message never waits on an AI call. The message (plus a few earlier ones for context) goes to TypeSafe’s Jev, which scores seven separate signals, personal attack, contempt, passive aggression, dismissiveness, motive attribution, inflammatory wording and retaliation, plus an overall hostility score.

Jev only scores, it doesn’t decide anything. Our own code takes those scores and puts the room into one of four states, clear, borderline, trigger or unavailable. Two borderline messages close together (within the last six) also count as a trigger, since people are often snippy before they’re outright rude. If Jev is down the room just counts as unavailable and chat carries on like nothing happened.

On a trigger, the room flips from calm to “mediating” in a single database update, and only whoever actually made that change gets to ask for a reply. So if two people kick off at the same time you still get exactly one intervention, not two. The reply is written by OpenAI (there’s an Anthropic adapter too), outside of any database transaction so the rest of the chat stays responsive, and the model has no tools and can’t see any other rooms. Once the reply is posted the room goes into a cooldown, and the mediator’s own messages never get scored, so it can’t set itself off.

The decisions I care about

I’d rather miss a reply than pay for one twice. If the server dies halfway through, anything nobody had picked up yet gets retried, but a request that was already being worked on is left to expire rather than generated again. Anything older than 60 seconds just expires into the cooldown.

The spending cap lives in the database. Every external call reserves from a saved allowance before it goes anywhere (by default 100 classifications and 20 replies per provider), failed calls still count, and the counters survive a restart. When it runs out, chat still works and the mediator goes quiet. It’s a cap on requests, not on money, so it’s not perfect, but it means a bug can’t run up a bill while I’m asleep.

Permissions get checked where the data actually goes. That’s the API, every WebSocket subscribe and send, and again on delivery. The release audit caught the first version still delivering messages to someone who’d left the room, which is exactly the kind of thing you’d never notice clicking around yourself. There’s now an end-to-end test for it over a real connection.

SQLite, one writer, on purpose. This is a small thing running on a free box, I don’t need PostgreSQL and a message broker for it. Keeping the model calls out of transactions is what lets a single connection handle a live chat fine. If it ever needed to scale out, that’s when it’d change.

A bug that only showed up on the real server

All the tests were green, but the container had never actually been run anywhere real. On the Oracle box it crash-looped on startup. Docker mounts tmpfs with noexec by default, and the SQLite driver unpacks a native library at startup that needs to be executable. The fix was a wee dedicated tmpfs that allows execution, only used by the driver, so /tmp stays locked down. Pretty good reminder that “the tests pass” and “it runs” are two different things.

Security and hosting

Server-side sessions, BCrypt passwords, CSRF protection (including on the WebSocket connect), a content security policy, size limits and rate limits per IP and per user. The container runs as a non-root user on a read-only filesystem, and only the Caddy proxy is reachable from the internet. The official Caddy image had nine fixable high / critical findings in Trivy, so the proxy gets rebuilt on patched libraries and that one scans clean.

Backups run nightly, get integrity-checked, encrypted and uploaded to private storage. The server can add backups but can’t read or delete them, so if someone got into the box they couldn’t wipe its history, and the decryption key isn’t on it. I’ve tested a restore into a separate copy.

Tests

134 backend tests and 16 frontend ones (on Node’s built-in test runner, no dependencies). Every model call is mocked in the suite, so running the tests costs nothing. On top of that there’s a script of about twenty checks against the live server, and a real run where the mediator’s message reached the other people in the room in two to three seconds.

What it doesn’t do yet

The replies aren’t properly measured. What I’ve verified is the plumbing, the replies I’ve seen read as neutral and specific, but that’s me eyeballing them, not a real measurement. There’s a labelled set of expected outcomes in the repo that isn’t wired into the tests yet, and that’s next.

It’s also not a finished product. Messages are stored unencrypted, and there’s no password reset, email verification, account deletion or moderation tools yet.
